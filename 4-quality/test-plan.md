# План перевірок

## 1. Статус документа

Продукт: CryptoFluctuation Intelligence Tracker.

Версія документа: 0.1.
Статус: початковий план для обговорення командою.

Документ визначає обсяг, порядок і умови перевірок.
Він не є звітом про успішне тестування.

Окремі ручні дії вже виконано під час підготовки
матеріалів прототипу. Їхні результати описано
в README прототипу та звіті про дефект BUG-001.

Повний набір перевірок ще не виконано.
Дати, виконавці та остаточні пріоритети потребують погодження.

## 2. Мета

Перевірити, чи допомагає перший MVP користувачу:

1. Знайти потрібну криптовалюту.
2. Переглянути її котирування та графік.
3. Змінити період графіка.
4. Переглянути новини й відкрити оригінал.
5. Зрозуміти походження та обмеження даних.

Окрема мета — виявити розбіжності між специфікацією
та наявним прототипом і зафіксувати їх без приховування.

Перевірки не мають підтверджувати прибутковість,
прогнозування ціни або правдивість усіх новин.

## 3. Об’єкти перевірки

- Інтерфейс наявного локального вебзастосунку.
- Пошук і відображення списку монет.
- Котирування та їх оновлення.
- Графіки й перемикання періодів.
- Новини та оригінальні посилання.
- Пояснення перевірки походження.
- Повідомлення про обмеження даних.
- Документація, діаграми та внутрішні посилання.
- Локальний API — після встановлення його фактичних маршрутів.
- Сховище — лише в окремому тестовому середовищі
  для відповідних перевірок.

Архітектурні документи та запропонований контракт API
не вважаються доказом фактичної реалізації.

## 4. Обсяг першого MVP

### 4.1. Функціональні вимоги

| Вимога | Що перевіряється |
|---|---|
| FR-01 | Список 15 монет, ціни, USDT, годинна зміна, джерело та пояснення MATIC/POL |
| FR-02 | Пошук за назвою й символом, регістр, очищення запиту, відсутність збігів |
| FR-03 | Планування оновлення кожні 10 секунд в активній видимій вкладці та відображення без перезавантаження |
| FR-04 | Відкриття графіка правильної монети, пара, джерело й час оновлення |
| FR-05 | Періоди 1 година, 4 години, 1 доба, 7 діб і повідомлення про помилку |
| FR-06 | Заголовок, видавець, доступна дата та відкриття оригіналу в новій вкладці |
| FR-07 | Перевірка HTTPS і відповідності домену видавцю; пояснення, що це не фактчек |
| FR-08 | Демонстраційні, застарілі, відсутні та недостатні дані без вигаданих результатів |

Перевірка FR-08 також охоплює заборону створення
нових дослідницьких сигналів на демонстраційних
або застарілих даних, якщо механізм сигналів
присутній у перевірюваній версії.

### 4.2. Нефункціональні вимоги

| Вимога | Підхід |
|---|---|
| NFR-01 | Вимірювання часу відповідей локального API з кешованими даними |
| NFR-03 | Перевірка основних екранів на ширинах 390 і 1440 CSS-пікселів |
| NFR-04 | Перевірка основного сценарію з потенційними користувачами поза командою |
| NFR-05 | Перевірка ізоляції автоматизованих операцій запису від робочої бази |
| NFR-06 | Контрольовані негативні сценарії та видимість попереджень |

NFR-02 щодо збереження позицій і журналу сигналів
перевіряється після включення відповідних
Should-функцій до обсягу версії.

Якщо потрібні умови відсутні,
перевірка позначається як заблокована,
а не як успішна.

## 5. Поза поточним обсягом

До першого MVP не входить повна перевірка:

- пояснюваних сигналів і їх журналу — FR-09–FR-11;
- навчальних позицій і статистики — FR-12–FR-16;
- освітньої довідки — FR-17;
- усіх мов інтерфейсу — FR-18.

Ці функції можуть бути присутні в прототипі,
але перевіряються окремо після погодження обсягу.

Не перевіряються як можливості продукту:

- реальне виконання біржових ордерів;
- зберігання коштів або приватних ключів;
- гарантований прибуток;
- достовірне передбачення майбутньої ціни;
- автоматичне встановлення правдивості новин;
- багатокористувацький режим та авторизація.

## 6. Види перевірок

### 6.1. Рев’ю документації

Перевірити:

- узгодженість бачення, SRS і меж MVP;
- однозначність критеріїв приймання;
- відповідність ідентифікаторів вимог;
- зв’язки вимог зі сценаріями та перевірками;
- роботу внутрішніх посилань і зображень;
- відокремлення запланованого від фактично виконаного;
- відсутність секретів і приватних даних;
- розрізнення проєктної архітектури та наявної реалізації.

Коментарі іншого учасника фіксуються фактично.
Погодження або рев’ю не вигадуються.

### 6.2. Функціональні ручні перевірки

Для кожного сценарію записати:

- передумови;
- вхідні дані;
- кроки;
- очікуваний результат;
- фактичний результат;
- статус;
- докази та пов’язані дефекти.

### 6.3. Негативні сценарії

Перевірити щонайменше:

- пошук без збігів;
- недоступність графіка;
- відсутність новин за успішного отримання порожньої відповіді;
- недоступність джерела новин;
- відсутність котирування;
- показ збережених даних після збою;
- демонстраційні дані;
- недостатність даних для аналізу;
- посилання з невідповідним доменом;
- посилання без HTTPS.

Порожній результат і збій джерела
не повинні подаватися як однаковий стан.

Негативні сценарії відтворюються контрольовано
в тестовому середовищі.

### 6.4. Адаптивність і доступність основних дій

Перевірити на ширинах 390 і 1440 CSS-пікселів:

- ринок;
- результати пошуку;
- графік і перемикання періодів;
- блок новин;
- повідомлення про помилки та обмеження.

Перевірити:

- відсутність горизонтального прокручування всієї сторінки;
- відсутність обрізання важливого вмісту;
- доступність кнопок і полів;
- відсутність перекриття основних дій;
- можливість пройти основний сценарій.

Локальне прокручування широкої таблиці допускається.

Один скриншот або відсутність реакції
на Shift і коліщатко не є достатнім доказом
повного виконання NFR-03.

### 6.5. Швидкодія

Для NFR-01:

1. Зафіксувати характеристики комп’ютера,
   версії середовища та перевірювану операцію API.
2. Підготувати кешовані дані.
3. Виконати 20 послідовних запитів.
4. Записати тривалість кожного.
5. Порахувати відповіді тривалістю не більше 1 секунди.

Ціль: щонайменше 19 із 20 відповідей
тривають не більше 1 секунди.

Умови:

- один користувач;
- клієнт і сервер на одному комп’ютері;
- зовнішні запити не входять у вимірювану операцію.

Цільовий критерій не є вже отриманим результатом.

### 6.6. Зрозумілість основного сценарію

Для NFR-04 залучити п’ять потенційних користувачів
поза командою.

Кожен учасник без допомоги за 5 хвилин має:

1. Знайти задану монету.
2. Відкрити її графік.
3. Відкрити оригінальну публікацію новини.
4. Пояснити попередження про демонстраційні
   або недоступні дані.

Ціль: щонайменше 4 з 5 учасників
виконують повний набір завдань.

Зафіксувати фактичні дії, відповіді, час і труднощі.
Не записувати очікувані відповіді як отримані.

Після включення FR-09 окремо перевірити,
чи розуміють учасники, що «підвищений ризик»
не обіцяє зростання ціни.

### 6.7. Безпека робочих даних

Для NFR-05:

- усі автоматизовані перевірки, які змінюють дані,
  мають використовувати окрему тестову базу;
- перед запуском потрібно перевірити фактичний шлях бази;
- якщо ізоляція не підтверджена, запуск забороняється;
- робочий застосунок потрібно штатно зупинити
  перед контрольним вимірюванням стану робочої бази;
- після двох послідовних запусків перевірок
  контрольна сума робочої бази має залишитися незмінною.

Якщо SQLite використовує додаткові файли WAL,
їх потрібно врахувати під час фіксації стану сховища.

Не використовувати «Скинути систему»
для підготовки скриншотів або перевірок на робочих даних.

### 6.8. Попередження про обмеження

Для NFR-06 заздалегідь визначити набір сценаріїв
із демонстраційними, застарілими та відсутніми даними.

У кожному виконаному сценарії перевірити:

- наявність відповідного попередження;
- зрозумілість стану;
- відсутність твердження про підтверджену доцільність покупки.

Ціль: попередження є у 100% визначених
і виконаних негативних сценаріїв.

Цей результат не означає усунення всіх фінансових ризиків.

## 8. Тестові дані

Для пошуку використовувати:

- `BTC`;
- `btc`;
- `Bitcoin`;
- порожній запит;
- `wwww` як приклад запиту без збігів.

Для графіків використовувати BTC
та щонайменше одну іншу доступну монету.

Для новин підготувати контрольовані приклади:

- публікація з відомою датою;
- публікація без дати;
- порожній список публікацій;
- збій джерела;
- HTTPS-посилання на відповідний домен;
- посилання на сторонній домен;
- посилання без HTTPS.

Синтетичні приклади позначаються як тестові.
Вони не подаються як справжні новини або поточні котирування.

Поріг застарілості даних потрібно погодити
та зафіксувати перед перевіркою відповідного сценарію.
Без визначеного порогу результат не вважається підтвердженим.

10. Після виправлень виконати повторні перевірки

- Визначено обсяг конкретного прогону.
- Відомі очікувані результати.

Якщо умови не виконано,
відповідні перевірки позначаються як заблоковані.

## 11. Умови завершення

Перевірка конкретного набору завершується, коли:

- кожен запланований тест має фактичний статус;
- результати й докази зафіксовано;
- виявлені дефекти оформлено;
- заблоковані та невиконані сценарії пояснено;
- залишкові ризики описано;
- рішення щодо прийнятності відомих дефектів
  погоджено відповідальними учасниками.

Завершення прогону не означає автоматичного
виконання всіх вимог або готовності релізу.

- Зовнішні джерела можуть бути недоступні.
- Ринкові дані змінюються між перевірками.
- Частина параметрів, зокрема поріг застарілості,
  ще потребує погодження.
- Реальні потреби користувачів ще не підтверджено інтерв’ю.
- Доступність контрольованих негативних сценаріїв
  залежить від тестового середовища.
- Скриншоти не замінюють перевірку поведінки.
- Перевірки в одному браузері не доводять сумісності з усіма.
- Наявна реалізація може відрізнятися
  від запропонованої архітектури та контракту API.
