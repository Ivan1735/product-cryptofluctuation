# BUG-003. Помилка API новин не має постійного відображення

## Статус і походження

Виправлено й повторно перевірено ШІ-асистентом в окремій переданій копії.
Встановлення цієї копії користувачем ще не підтверджене.
[Повторна перевірка і патч](../qa-known-bugs-retest.md).

Нижче збережено початкове відтворення до виправлення.

Виявив: ШІ-асистент у контрольованому прогоні за дорученням Івана.
Серйозність і пріоритет потребують командного погодження.
Вимоги й перевірки: FR-08; негативні підсценарії TC-15.
Дата завершення прогону (UTC): `2026-11-01T18:12:26.644Z`.
Копія і контрольні суми зазначені в [звіті](../qa-negative-states-report.md).

## Відтворення

Спочатку повернути /api/news HTTP 503 без попередніх новин. Окремо успішно завантажити контрольовані новини, потім повернути 503 і натиснути оновлення новин. Дочекатися зникнення toast (6,5 с).

Умови: ізольована SQLite, Chromium, тестові HTTP-відповіді.
Це не повідомлення про справжній збій зовнішнього видавця.

## Очікувано

При початковому збої є зрозумілий стан помилки. Якщо збережено старі новини, видиме обмеження оновлення залишається біля них до успішного отримання, а не тільки в тимчасовому сповіщенні.

## Фактично

Без кешу залишається skeleton без повідомлення. Після успіху ручний збій показує toast «Не вдалося оновити новини»; пізніше він зникає, старі статті та позитивні статуси джерел залишаються без постійної позначки збою.

## Спостереження в коді

loadNews у catch показує тільки toast для manual=true; окремого стану помилки/застарілості новин немає. Backend timeout RSS і browser HTTP 503 API — різні контрольовані сценарії.

Це історичне пояснення за кодом до виправлення; поточні зміни описані у повторній перевірці.

## Подальша дія та повторна перевірка

Зберігати стан помилки й час останнього успішного оновлення; показувати сталий текст у блоці новин. Не втрачати попередні статті за можливості, але явно позначати обмеження; прибирати помилку тільки після успіху.

Повний формальний TC-15 не позначається виконаним цим окремим підсценарієм.
