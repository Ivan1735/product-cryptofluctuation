# ADR-0002. SQLite для локального зберігання даних

## Статус

Запропоновано.

Дата рішення: не зафіксована.
Погодження командою: ще не зафіксовано.

Документ описує пропозицію щодо постійного сховища.
Використання SQLite в наявному прототипі
не означає автоматичного погодження цього ADR.

## Контекст

Продукт розрахований на локальне навчальне використання
одним користувачем.

Для наступних розширень потрібно зберігати:

- початкові записи дослідницьких сигналів;
- результати сигналів через 1, 4 та 24 години;
- активні навчальні позиції;
- завершені навчальні угоди.

Підтверджені записи мають зберігатися після штатного перезапуску.

Закриття навчальної позиції потребує узгодженого виконання:
створення завершеної угоди та прибирання активної позиції.

Поточні котирування й новини можуть перебувати в кеші.
Їх не обов’язково зберігати як постійну історію.

## Архітектурне питання

Яке сховище забезпечить збереження й узгодженість
навчальних даних без зайвої інфраструктури?

## Критерії вибору

- Простота локального налаштування.
- Відсутність окремого сервера бази даних.
- Підтримка транзакцій.
- Можливість задавати ключі та обмеження.
- Придатність для одного користувача.
- Можливість відокремити тестові дані від робочих.

## Розглянуті варіанти

### Варіант 1. SQLite

Вбудована реляційна база даних у локальному файлі.

Переваги:

- не потрібен окремий сервер;
- доступна через sqlite3 стандартної бібліотеки Python;
- підтримує транзакції та обмеження цілісності;
- підходить для невеликого локального застосунку.

Недоліки:

- одночасні операції запису потребують контролю;
- файл потребує захисту й резервного копіювання;
- для іншого масштабу використання може знадобитися міграція.

### Варіант 2. PostgreSQL

Окремий сервер реляційної бази даних.

Переваги:

- розвинені можливості керування доступом;
- придатність для багатокористувацьких систем;
- ширші можливості одночасної роботи.

Недоліки:

- додаткове встановлення та адміністрування;
- окремі облікові дані й налаштування;
- надмірна інфраструктура для поточного локального обсягу.

### Варіант 3. JSON-файли

Зберігання записів у звичайних файлах.

Переваги:

- зрозумілий формат;
- простий перегляд невеликої кількості даних.

Недоліки:

- цілісність і транзакційність потрібно забезпечувати окремо;
- складніше контролювати дублювання та зв’язки;
- незручно підтримувати вибірки й місячну статистику;
- ризик часткового перезапису потребує окремого вирішення.

### Варіант 4. Лише пам’ять процесу

Дані існують до завершення роботи застосунку.

Переваги:

- мінімальне налаштування;
- придатність для тимчасового кешу.

Недоліки:

- втрата даних після перезапуску;
- невідповідність вимозі збереження підтверджених записів;
- непридатність для постійного журналу й навчальних угод.

## Запропоноване рішення

Використати SQLite як постійне локальне сховище.

Доступ до даних організувати через логічний модуль Persistence.

Передбачити:

- окремий шлях для робочої бази;
- окремий шлях для тестової бази;
- транзакції для пов’язаних змін;
- параметризовані SQL-запити;
- обмеження унікальності для захисту від дублювання;
- перевірку доступності сховища та обробку помилок.

Конкретні таблиці, типи полів та індекси
потрібно визначити в моделі даних.

## Обґрунтування

SQLite відповідає локальному однокористувацькому обсягу
та не потребує додаткового сервера.

Транзакції дозволяють пов’язати операції закриття позиції,
щоб невдача не залишала частково змінений стан.

Реляційна модель придатна для зв’язку сигналів
із результатами та для групування навчальних угод.

Вибір SQLite не скасовує потребу
у валідації, резервному копіюванні та перевірках.

## Правила використання

### Узгодженість операцій

- Створення завершеної угоди та видалення активної позиції
  виконуються в одній транзакції.
- Помилка спричиняє відкат пов’язаних змін.
- Успіх повідомляється лише після успішного завершення запису.
- Стан позиції повторно перевіряється всередині транзакції.

### Захист від дублювання

- Для початкової позиції допускається
  не більше однієї завершеної угоди.
- Для пари «сигнал — горизонт» допускається
  не більше одного результату.
- Повторний запит не повинен створювати дубль.

### Незмінність сигналів

- Початкові умови сигналу не переписуються.
- Подальші результати зберігаються окремо.
- Версія правил аналізу залишається частиною початкового запису.

### Відокремлення операцій видалення

- Видалення помилкової позиції не створює завершеної угоди.
- Скидання навчальних угод не видаляє сигнали та їхні результати.
- Масове очищення потребує явного підтвердження.

### Зовнішні ключі

Якщо модель використовує зовнішні ключі SQLite,
їх перевірку потрібно явно вмикати для кожного з’єднання.

Поведінку видалення пов’язаних записів
потрібно визначити в моделі даних.

### Часові позначки

Час зберігається в узгодженому форматі з UTC.
Місячна статистика визначається за часом закриття угоди.

### Ціни та кількості

Точне подання десяткових значень потрібно визначити
до фіксації схеми.

Не можна вважати, що використання SQLite автоматично
усуває похибки чисел із плаваючою крапкою.

## Безпечність даних

- Робоча база не додається до публічного репозиторію.
- Тестові операції не виконуються на робочій базі.
- Введені значення не вставляються безпосередньо в SQL.
- Назви таблиць та операцій вибираються
  з визначеного програмою переліку.
- Файл зберігається з доступом лише для потрібного середовища.
- У сховищі не передбачено реальних коштів,
  приватних ключів або торгових API-ключів.

SQLite не забезпечує автоматичного шифрування файла
лише завдяки факту використання бази даних.

Порядок резервного копіювання та відновлення
потрібно описати окремо.

## Наслідки

### Позитивні

- Простіше локальне налаштування.
- Підтримка транзакцій.
- Можливість обмежень цілісності.
- Збереження даних незалежно від кешу.
- Просте створення окремої тестової бази.

### Негативні

- Потрібно контролювати конкурентні записи
  між HTTP-запитами та фоновими задачами.
- Потрібно керувати з’єднаннями й блокуваннями.
- Пошкодження або видалення файла може призвести
  до втрати даних без резервної копії.
- Зміни схеми потребують керованого переходу між версіями.

## Перевірка відповідності

Перед погодженням рішення потрібно перевірити:

1. Збереження підтверджених записів
   після 10 штатних перезапусків на тестовій базі.
2. Відкат незавершеної операції закриття позиції.
3. Відсутність дубля при повторному закритті.
4. Унікальність результату для сигналу та горизонту.
5. Збереження журналу сигналів після скидання угод.
6. Використання окремої бази для перевірок запису.
7. Незмінність робочих даних після таких перевірок.
8. Відновлення з підготовленої тестової резервної копії.

Для перевірки незмінності робочої бази потрібно
врахувати режим журналювання та супровідні файли SQLite.
Методику порівняння узгоджують до запуску перевірки.

Фактичні результати поки не зафіксовані.

## Умови перегляду рішення

Рішення потрібно переглянути, якщо з’явиться потреба:

- в одночасній роботі багатьох користувачів;
- у кількох серверних процесах із суттєвим навантаженням запису;
- у віддаленому централізованому сховищі;
- у розширеному керуванні доступом;
- у вимогах до доступності, які не забезпечує локальний файл.

Перехід на іншу базу потребуватиме окремого ADR
та плану міграції даних.
