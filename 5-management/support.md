# Супровід прототипу

## Статус і межі

Версія документа: 0.1. Початковий порядок для погодження командою.
Прототип призначений для локального навчального використання одним користувачем.
Публічна служба підтримки, цілодобове чергування та гарантований час відповіді не передбачені.
Описані процедури ще потрібно перевірити на конкретній версії застосунку.

## Як повідомити про проблему

Передайте команді опис або створіть Issue у репозиторії,
якщо цей канал погоджено. Додайте:

- розділ і послідовність дій;
- очікуваний та фактичний результат;
- версію застосунку, якщо відома;
- браузер, ОС і розмір області перегляду;
- фактичний час виникнення;
- текст помилки та скриншот без приватних даних.

Не додавайте робочу базу, паролі, токени або приватні ключі.
Якщо версія чи причина невідома, прямо зазначте це.
Публічний Issue не є місцем для приватних журналів і секретів.

## Опрацювання звернення

1. Зафіксувати звернення та доступні докази.
2. Оцінити вплив і терміновість; не обіцяти непогоджений строк.
3. Спробувати відтворити на окремому тестовому середовищі.
4. За підтвердженої розбіжності створити bug report зі зв’язком із вимогою.
5. Визначити відповідального після погодження.
6. Підготувати виправлення або пояснити обмеження.
7. Виконати повторну перевірку та потрібну регресію.
8. Оновити документацію, статус і історію змін.

Сам факт зміни коду не означає, що дефект перевірено й закрито.
Знайдена розбіжність може залишитися в беклозі навчального проєкту;
її не можна позначати виправленою без доказу.

## Типові ситуації

| Ситуація | Безпечна початкова дія |
|---|---|
| Локальна сторінка не відкривається | Перевірити запуск сервера й адресу; не змінювати базу |
| Джерело недоступне | Зафіксувати повідомлення, час і джерело; не вигадувати значення |
| Дані застаріли | Перевірити справжній час отримання; UI цієї копії попереджає після 60 с. Не приймати кеш за поточне котирування |
| Публікацій немає | За успішної відповіді джерел це порожній стан, не обов’язково збій |
| Помилка оновлення новин | Постійне попередження й час останнього успіху мають залишатися біля кешу; спробувати оновлення пізніше, не видаляти БД |
| Порожній пошук без пояснення | Змінити або очистити запит. У старій копії врахувати BUG-001; у переданій виправленій копії повідомлення підтверджене користувачем |
| Графік не завантажився | Зберегти помилку й параметри; відтворювати збій на тестовому середовищі |
| Підозра на втрату даних | Припинити операції запису та звернутися до відповідального |
| Розкрито секрет | Негайно відкликати або замінити його; видалення останнього рядка не очищує історію Git |

Не використовуйте «Скинути систему» як універсальне виправлення.

## Резервне копіювання й відновлення

Перед змінами сховища потрібно мати перевірену резервну копію.
Конкретні шляхи, інструмент копіювання, періодичність і строк зберігання
ще не погоджені; гарантовані RPO/RTO не встановлені.

Для SQLite не слід копіювати лише основний файл під час активного запису.
Потрібно обрати узгоджений спосіб: штатний backup-механізм SQLite
або контрольоване зупинення застосунку з урахуванням стану WAL.
Процедуру спочатку перевіряють на тестовій копії.

Відновлення:

1. Припинити записи та зберегти поточний стан для аналізу.
2. Вибрати відому резервну копію та сумісну версію застосунку.
3. Відновити в окремому тестовому місці.
4. Перевірити цілісність і потрібні записи.
5. Лише після перевірки погодити заміну робочої бази.

Не публікуйте резервні копії в GitHub.
Не стверджуйте, що відновлення можливе, поки його не перевірено.

## Оновлення

- Зафіксувати поточну версію та резервну копію перед змінами даних.
- Перевірити зміни на тестовому середовищі.
- Не виконувати неперевірені міграції на робочій базі.
- Відокремлювати випуск документації від версії застосунку.
- Описувати відомі обмеження й результати перевірок.
- Планувати відкат даних окремо: відкат Git не відновлює базу автоматично.

## Перевірена копія та залишкові межі

BUG-001–004 виправлено й повторно перевірено в [переданій копії](../4-quality/qa-known-bugs-retest.md).
Користувач показав запуск нового інтерфейсу; це не повтор усіх негативних сценаріїв.
Ринковий поріг UI 60 с — робоче рішення цієї копії, що потребує погодження;
дослідницький захист 35 с не послаблено. Нові повідомлення UA/EN,
для решти мов — EN fallback. Збої публічних джерел залишаються можливими.
Один тест збереження після перезапуску не підтверджує повного відновлення з backup
або гарантій RPO/RTO.
