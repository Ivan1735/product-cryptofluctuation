# Правила валідації даних

## 1. Статус документа

Продукт: CryptoFluctuation Intelligence Tracker.
Версія документа: 0.1.
Статус: проєктні правила для обговорення командою.

Документ описує очікувані перевірки введення,
зовнішніх даних і переходів стану.

Наявність правила в цьому документі
не підтверджує його реалізації в застосунку.

Відповідність наявного прототипу цим правилам
потрібно перевірити окремо.

Правила для Should- і Could-функцій застосовуються
після включення цих функцій до обсягу версії.

## 2. Мета

Не допустити:

- створення некоректних навчальних записів;
- підміни недоступних значень нулем;
- використання демонстраційних даних як актуальних;
- створення сигналів на застарілих даних;
- дублювання завершених угод;
- помилкового підтвердження походження новин;
- прихованої втрати або зміни даних.

## 3. Загальні принципи

### 3.1. Клієнтська та серверна перевірка

Клієнтська перевірка допомагає користувачу,
але не замінює серверну.

Сервер повторно перевіряє всі дані,
які впливають на сховище або обчислення.

Значення з браузера та зовнішніх джерел
не вважаються довіреними лише через спосіб їх отримання.

### 3.2. Відсутні значення

NULL означає невідоме або недоступне значення.

Не можна замінювати нулем:

- відсутню ціну;
- невідомий результат сигналу;
- недоступну статистику;
- невідому дату.

Порожній список, збій отримання
та ще не готовий результат — різні стани.

### 3.3. Десяткові числа

Для цін, кількостей і навчальних результатів
використовується десяткова арифметика.

Після розбору перевіряється:

- чи значення є числом;
- чи воно скінченне;
- чи відповідає допустимому діапазону;
- чи відповідає погодженій точності.

NaN та Infinity відхиляються.

Для ціни й кількості потрібне значення більше нуля.

Для відсоткової зміни та результату угоди
від’ємні й нульові значення можуть бути коректними.

### 3.4. Формат введення чисел

Проєктна пропозиція для API:
десяткові числа передаються рядками з крапкою
без розділювачів тисяч.

Приклад: `"1234.56"`.

Підтримку десяткової коми в інтерфейсі
потрібно погодити окремо.

Не можна мовчки перетворювати неоднозначне введення
на інше число.

### 3.5. Час

Час зберігається й порівнюється в UTC.

Перевіряються:

- коректність формату;
- наявність часової зони або однозначного правила перетворення;
- відповідність часових полів їх призначенню.

Час отримання даних не видається
за час публікації або спостереження джерела.

### 3.6. Повідомлення про помилки

Повідомлення має:

- пояснювати проблему;
- бути пов’язаним із відповідним полем або дією;
- не розкривати секрети, SQL або внутрішні трасування;
- не стверджувати успіх після невдалої операції.

Некоректний запит не повинен частково змінювати дані.

## 4. Правила першого MVP

### VAL-01. Підтримувана монета

- Вимоги: FR-01, FR-04.
- Перевірка:
  символ має відповідати активу з підтримуваного довідника.
- За помилки:
  повернути зрозуміле повідомлення;
  не підставляти мовчки іншу монету.
- Важливо:
  користувацький символ не використовується
  для довільного формування зовнішньої адреси.
- Перевірки: TC-01, TC-07.

### VAL-02. Відповідність символу торговій парі

- Вимога: FR-01.
- Перевірка:
  пара визначається погодженим відображенням довідника.
- Для MATIC:
  використовується POLUSDT з явним поясненням міграції.
- За помилки:
  котирування не показується як правильне для іншого активу.
- Перевірка: TC-02.

### VAL-03. Пошуковий запит

- Вимога: FR-02.
- Перевірка:
  пошук виконується за назвою або символом
  без залежності від регістру.
- Порожній запит:
  повертає повний список.
- Відсутність збігів:
  показується повідомлення про відсутність результатів.
- Проєктна пропозиція:
  крайні пробіли обрізаються;
  запит лише з пробілів прирівнюється до порожнього.
- Статус пропозиції щодо пробілів:
  потребує погодження та узгодження із SRS.
- Перевірки: TC-03–TC-05.
- Відомий дефект:
  BUG-001 — повідомлення про відсутність збігів
  не показано для запиту `wwww`.

### VAL-04. Отримане котирування

- Вимоги: FR-01, FR-08.
- Перевіряються:
  - відповідність монеті та парі;
  - скінченна додатна ціна;
  - валюта котирування;
  - джерело;
  - час отримання;
  - коректність доступної годинної зміни.
- Якщо годинна зміна недоступна:
  вона не підміняється вигаданим значенням.
- Некоректна відповідь:
  не публікується як актуальне котирування.
- Перевірки: TC-01, TC-15.

### VAL-05. Стан і свіжість даних

- Вимога: FR-08.
- Перевіряються:
  походження, час отримання,
  доступний час спостереження та результат оновлення.
- Демонстраційні дані:
  мають видиму позначку.
- Збережені значення після збою:
  мають час останнього успішного отримання
  та попередження про можливу неактуальність.
- Дані без підтвердженої придатності:
  не використовуються для створення нового сигналу.
- Відкрите питання:
  поріг застарілості й політика використання часових полів
  ще потребують погодження.
- Перевірки: TC-14–TC-16.

### VAL-06. Період графіка

- Вимога: FR-05.
- Допустимі періоди:
  1 година, 4 години, 1 доба, 7 діб.
- Перевірка:
  сервер приймає лише погоджені значення параметра періоду.
- За помилки:
  запит відхиляється з поясненням;
  інший період не підставляється мовчки.
- Період перегляду не ототожнюється з кроком свічки.
- Перевірка: TC-08.

### VAL-07. Дані графіка

- Вимоги: FR-04, FR-05, FR-08.
- Перевіряються:
  - відповідність активу, парі та запитаному періоду;
  - коректність часових значень;
  - скінченні додатні ціни;
  - порядок точок за часом;
  - відсутність дублів однієї свічки.
- Неповна свічка:
  може змінюватися та не подається як остаточна.
- Некоректні або відсутні дані:
  не заповнюються вигаданими точками.
- Перевірки: TC-07–TC-09.

### VAL-08. Реквізити новини

- Вимога: FR-06.
- Перевіряються:
  непорожній заголовок, заявлений видавець
  та придатне посилання на публікацію.
- Невідома або некоректна дата:
  не замінюється вигаданою;
  відображається як невідома, якщо картку можна показати.
- Зовнішній заголовок:
  відображається як текст,
  а не виконується як HTML або JavaScript.
- Відкриття оригіналу:
  у новій вкладці.
- Перевірки: TC-10–TC-11.

### VAL-09. Безпечна адреса новини

- Вимоги: FR-06, FR-07.
- Перевірка:
  адреса розбирається стандартним URL-парсером.
- Проєктне правило безпеки:
  для посилань новин допускаються лише HTTP та HTTPS.
- Схеми javascript, data та file:
  не створюють активного посилання.
- Відсутність HTTPS:
  не дає позитивного результату перевірки походження.
- Проєктний захід:
  нова вкладка не повинна отримувати керування
  початковою вкладкою через opener.
- Ці заходи не доводять правдивості публікації.
- Перевірки: TC-10, TC-12.

### VAL-10. Відповідність домену видавцю

- Вимога: FR-07.
- Перевірка:
  аналізується фактичний hostname адреси,
  а не довільна наявність назви видавця в рядку.
- Позитивний результат:
  потребує HTTPS і відповідності погодженому домену.
- Сторонні домени та домени-імітації:
  не позначаються як підтверджені.
- Приклад:
  адреса `https://cointelegraph.com.attacker.example/news`
  не належить домену `cointelegraph.com`.
- Відкриті питання:
  правила піддоменів, міжнародних доменів
  і перенаправлень потрібно погодити.
- Пояснення:
  відповідність домену не є фактчеком.
- Перевірки: TC-12–TC-13.

### VAL-11. Порожній список і помилка джерела

- Вимоги: FR-06, FR-08.
- Успішна порожня відповідь:
  показується як відсутність публікацій.
- Збій:
  показується як недоступність або помилка оновлення.
- За наявності раніше отриманих новин:
  факт збою не приховується.
- Не допускається:
  створення вигаданих публікацій для заповнення блоку.
- Перевірки: TC-11, TC-15.

## 5. Правила розширень

### VAL-12. Придатність даних для сигналу

- Вимоги: FR-08, FR-09.
- Перед створенням перевіряються:
  достатність даних, їх походження та свіжість.
- Демонстраційні або застарілі дані:
  не створюють нових дослідницьких сигналів.
- Недостатні дані:
  дають явний стан недостатності, а не вигаданий аналіз.
- Перевірки: TC-16–TC-17.

### VAL-13. Незмінність початкового сигналу

- Вимога: FR-10.
- Обов’язкові поля:
  монета, час створення, початкова ціна,
  тип сигналу та версія правил.
- Зберігаються знімки:
  аргументів, ризиків і відсутніх даних.
- Після створення:
  початкові умови не змінюються.
- Не допускається:
  створення сигналу заднім числом
  під виглядом отриманого в реальному часі.
- Перевірка: TC-18.

### VAL-14. Горизонти результатів сигналу

- Вимога: FR-11.
- Допустимі горизонти:
  1, 4 та 24 години.
- Для пари сигнал і горизонт:
  допускається не більше одного запису результату.
- До цільового часу:
  показується очікування.
- Недоступний результат:
  не підміняється нулем.
- Для отриманого результату:
  зберігаються цільовий і фактичний час спостереження.
- Правило вибору спостереження після цільового часу
  та допустиме запізнення ще потрібно погодити.
- Перевірки: TC-19–TC-20.

### VAL-15. Розрахунок зміни ціни

- Вимога: FR-11.
- Початкова ціна:
  скінченне число більше нуля.
- Формула:
  `(подальша ціна - початкова ціна) / початкова ціна × 100`.
- Результат:
  може бути додатним, від’ємним або нульовим.
- За відсутності потрібної ціни:
  обчислення не виконується.
- Зміна ціни:
  не називається чистим прибутком.
- Перевірка: TC-20.

### VAL-16. Створення навчальної позиції

- Вимога: FR-12.
- Перевіряються:
  підтримувана монета, кількість і ціна входу.
- Кількість і ціна:
  скінченні додатні десяткові числа.
- Порожні, нечислові, нульові та від’ємні значення:
  відхиляються з поясненням.
- За помилки:
  запис у сховищі не створюється.
- Додавання:
  не надсилає реального біржового ордера.
- Перевірки: TC-21–TC-22.

### VAL-17. Закриття навчальної позиції

- Вимога: FR-13.
- Перед закриттям перевіряються:
  існування активної позиції та доступність потрібної ціни.
- Ціна закриття:
  не вигадується.
- Зміни виконуються атомарно:
  завершена угода створюється,
  а позиція перестає бути активною.
- За помилки запису:
  операція відкочується.
- Повторний запит:
  не створює дубль завершеної угоди.
- Перевірки: TC-23–TC-24.

### VAL-18. Видалення помилкової позиції

- Вимога: FR-14.
- Перевірка:
  вибрана активна позиція існує.
- Видалення:
  не створює завершеної угоди.
- Результати інших завершених угод:
  залишаються без змін.
- Відповідь для відсутнього запису
  узгоджується з контрактом API.
- Перевірка: TC-25.

### VAL-19. Скидання навчальних угод

- Вимога: FR-15.
- Передумова:
  явне підтвердження користувача.
- Після підтвердження:
  очищуються активні та завершені навчальні угоди.
- Журнал сигналів:
  зберігається.
- Після скасування:
  дані не змінюються.
- Перевірки: TC-26–TC-27.

### VAL-20. Місячна статистика

- Вимога: FR-16.
- Джерело:
  лише завершені навчальні угоди.
- Групування:
  за місяцем закриття в UTC.
- Видалені помилкові позиції:
  не включаються.
- Без угод:
  показується порожній стан.
- Різні валюти:
  не додаються без погодженого правила конвертації.
- Перевірки: TC-28–TC-29.

### VAL-21. Освітні пояснення

- Вимога: FR-17.
- Для кожного передбаченого терміна:
  визначення, приклад і застереження.
- Приклади:
  не подаються як персональна рекомендація реальної угоди.
- Перевірка: TC-30.

### VAL-22. Вибір мови

- Вимога: FR-18.
- Перевірка:
  код мови належить погодженому списку.
- Перемикання:
  без повного перезавантаження.
- Постійні написи:
  відповідають вибраній мові.
- Мови:
  мають текстові назви, а не лише прапорці.
- Непідтримуваний код:
  обробляється явно за погодженим правилом.
- Перевірка: TC-31.

## 6. Обмеження введення та безпечна обробка

Додаткові проєктні правила:

- SQL-запити використовують параметри,
  а не склеювання введення з SQL.
- Значення від зовнішніх джерел екрануються
  під час відображення.
- Помилки не розкривають секрети й внутрішні шляхи.
- Зміни сховища виконуються транзакційно.
- Запит не може обирати довільний файл бази даних.

Граничні довжини рядків, розміри відповідей,
максимальні кількості й ціни
потребують окремого погодження.

Ці правила є проєктними заходами.
Вони не означають проведення аудиту безпеки.

| Новини та походження | TC-10–TC-13, TC-15 |
| Демонстраційні й недостатні дані | TC-14–TC-16 |
| Сигнали | TC-17–TC-20 |
| Навчальні позиції | TC-21–TC-27 |
| Статистика | TC-28–TC-29 |
| Освітня довідка й мови | TC-30–TC-31 |

Негативні перевірки для додаткових проєктних правил,
які ще не охоплені тест-кейсами,
потрібно додати після погодження цих правил.

## 9. Невирішені питання

Потрібно погодити:

1. Поріг застарілості та джерело часу для його визначення.
2. Точність, масштаб і округлення десяткових значень.
3. Підтримку десяткової коми в інтерфейсі.
4. Максимальні довжини й числові межі.
5. Обробку запитів лише з пробілів.
6. Допустимі піддомени й політику перенаправлень новин.
7. Спосіб вибору спостереження для результату сигналу.
8. Обробку невідомого коду мови.
9. Відповідність правил фактичній реалізації та API.

До погодження параметри не подаються
як остаточні вимоги.

## 10. Поточний стан перевірки

Формальна перевірка всіх правил не виконана.

Зафіксовано відому розбіжність:

- для запиту `wwww` не показано повідомлення
  про відсутність результатів;
- дефект оформлено як BUG-001;
- виправлення й повторну перевірку не виконано.

Інші попередні спостереження наведено
у звіті про перевірки.

## 11. Подальші дії

- Провести рев’ю правил.
- Узгодити відкриті параметри.
- Порівняти правила з наявною реалізацією.
- Доповнити тест-кейси граничними прикладами.
- Виконати перевірки в безпечному середовищі.
- Оформити фактичні розбіжності.
- Оновити SRS, API та модель даних
  після погоджених змін.
